The problem, the build, the result

Problem. Indian businesses must register every B2B invoice with the government e-invoice system (IRP) and get an IRN back. For a company on iDempiere, that meant keying invoices into a portal by hand, or building a one-off integration for each project.

Approach. An OSGi plugin maps each completed invoice to the IRP request and checks it against the official JSON schema before any API call, so errors come back in plain language and name the invoice line. It then registers the invoice through Whitebooks and stores the IRN, signed invoice and QR code on the document. Every attempt is kept with its raw response.

Result. One invoice or a whole date range can be registered from a single process, and each invoice in a batch succeeds or fails on its own. IRNs can be cancelled within the 24-hour window, and invoices with an active IRN are protected from being voided by mistake. Developed and tested against the Whitebooks sandbox.

The hard part: an IRN that already exists

The IRP will not register the same invoice twice, so it answers with an error saying the IRN already exists. That can happen when a call succeeded at the IRP but the response never made it back, leaving iDempiere with no IRN for an invoice that already has one. Retrying can never fix this.

The plugin treats that error as a recovery path. It fetches the existing IRN from the IRP and checks that document type, number, date, both GSTINs and the total all match the invoice before attaching it. If anything differs, it refuses and reports the mismatch, so a wrong IRN is never silently stored on an invoice.

From completed invoice to IRN

  1. Complete the invoiceFill the few e-invoice fields that apply: supply type, reverse charge, export or e-way details.
  2. Run the process"Generate E-Invoice (IRN)" for one invoice, or a date range for many.
  3. Map & validateThe invoice becomes the IRP request and is checked field by field, with readable errors.
  4. Register with IRPAuthenticates, calls GENERATE through Whitebooks and handles token expiry.
  5. Stored on the invoiceIRN, acknowledgement, signed invoice, QR and e-way bill details are saved.

Common questions

Does the plugin work with iDempiere 13?

Yes. It is built for iDempiere 13 on Java 17 and PostgreSQL, as an OSGi plugin installed like any other iDempiere bundle.

Which API provider does it use?

Whitebooks GSP. You use your own Whitebooks credentials and your own GSTIN; the plugin does not route invoices through anyone else.

Does it replace my GST Suvidha Provider (GSP)?

No. It is the integration between iDempiere and the e-invoice system. You still need a Whitebooks account and an API user on the e-invoice portal.

Is B2C supported?

No. The IRP does not accept B2C invoices, so in batch mode they are skipped, and a single invoice without a buyer GSTIN returns a clear error (exports excepted).

What if an invoice was sent by mistake?

Reverse it and cancel the IRN within 24 hours. After that, issue a credit memo. The plugin enforces this so users do not end up with an inconsistent state.

Are my IRP credentials safe?

Password, client ID and secret are stored in encrypted columns and kept out of the change log. Encryption depends on your iDempiere Secure class, so the documentation explains how to verify it before entering production credentials.

Can it be customized for my setup?

Mapping rules, extra fields and workflow changes can be discussed. Tell me what you need when you get in touch.
